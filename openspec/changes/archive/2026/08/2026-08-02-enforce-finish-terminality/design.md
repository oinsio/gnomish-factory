# Design: enforce-finish-terminality

## Context

Driven by FR1–FR6 and NFR-R1–R3, NFR-P1 of this change's proposal. The lifecycle must be one-way (FR1), but today a human relabeling a Delivered issue back to Ready makes the GitHub adapter report `returned = true` (any REPORT marker counts, including the finishing one — `GithubReturnedFactReader`), which *prioritizes* the task for re-claiming, while the in-memory adapter reports `returned = false` for the same history. The root cause sits in the marker vocabulary: park and finish — two opposite lifecycle events — share the single `report` marker kind (a design-D9 accident), distinguished only implicitly by the presence of the structural `reason` field on park markers. The project is pre-production: no live tracker threads must stay parseable, so the wire vocabulary itself is changeable.

## Goals / Non-Goals

**Goals:**
- One derivation rule per fact, identical across adapters, enforced by the shared contract suite.
- Decline behavior that is stateless (NFR-R3), idempotent at the state level (NFR-R1), and free of extra GitHub API reads (NFR-P1).

**Non-Goals:**
- No changes to claim-lease boundary *mechanics* from add-claim-heartbeat (the session-ending boundary anchor stays; the boundary kind list changes with D1's vocabulary split, the algorithm does not).
- No migration/compat path for threads written with the old dual-use `report` kind — pre-production, none need to survive.

## Decisions

**D1 — Split the dual-use `report` marker kind into dedicated `park` and `finish` kinds; retire `report`.** `GithubStateWrites.park` writes a `park`-kind marker (still carrying the `reason` field as its payload), `finish` writes a `finish`-kind marker; the `report` kind leaves the vocabulary. Derivations become structural: `finished` = "history contains a FINISH marker"; `returned` = "history contains a PARK or STALE_CLAIM_REMOVED marker" (FR1, FR2). Consumers updated in step: the claim-boundary lists (`GithubClaimComment.isBoundary`, `GithubClaimLease.latestBoundaryIndex`) replace REPORT with PARK + FINISH (same behavior — both end a session), and `GithubParkReason` matches on kind PARK alone. *Rationale:* the decline protocol (D3) makes misreading this discrimination actively destructive — a task wrongly judged finished is autonomously flipped to Delivered by the factory. Discriminating by the *absence* of a nullable field is negative-space encoding: `render(REPORT, id, at, text)` without the reason argument is the natural-looking call, so one forgotten argument in a future write path silently means "finish" and bricks a live task (or breaks the escalation round-trip in the opposite direction). A dedicated enum kind makes the dangerous choice explicit and diff-visible, matches the vocabulary's own one-kind-per-lifecycle-event structure (CLAIM, ABORT, PROGRESS, STALE_CLAIM_REMOVED...), and removes the need for a javadoc-pinned wire invariant plus contract scenarios defending a convention. *Alternative rejected — reason-based discrimination (no wire change):* a REPORT with `reason` is a park, without is a finish. Zero rework and backward-compatible with existing threads, but that compatibility is worthless pre-production, while the implicit invariant is load-bearing forever at the most dangerous spot in the system. *Alternative rejected — add `finish` but keep park on `report`:* half measure; park stays on a dual-use kind name and `GithubParkReason` keeps its reason-presence check, preserving two implicit discriminators instead of zero.

**D2 — `finished` is an adapter-reported fact; core decides and acts.** `ReadyTask` gains a `finished` boolean next to `returned`; `TrackerTask` (the `fetchTask` result) gains the same fact for the explicit-take path (FR5). *Rationale:* the tracker-port philosophy (add-tracker-port D10) is "raw feed + facts from the adapter, policy in core"; silently dropping finished tasks inside `listReady` would hide the decline obligation and leave the task stranded in Ready forever. *Alternative rejected:* adapter-side filtering — violates D10 and makes FR4's decline impossible to trigger.

**D3 — One new port operation: decline-finished (restore terminal status + post explanation).** Signature shape: `declineFinished(TaskRef ref, String message)`; core composes the human text (mirroring `park`, where core supplies the report). GitHub: label transition Ready → Delivered, then a `NOTE`-kind marker comment carrying the message. In-memory: state → `Finished`, plus a `NOTE` correspondence entry. *Rationale:* the comment MUST NOT be a PARK or FINISH marker — those feed the `returned`/`finished` derivations (D1); `NOTE` is the existing out-of-band kind with no derivation weight. *Alternative rejected:* reusing `finish(ref, summary)` — its GitHub write transitions Working → Delivered and posts a FINISH marker; wrong source state, and the decline would masquerade as a second completion in the recorded history.

**D4 — Decline fires in the feed cycle and in explicit take, not in `FeedPolicy`.** `FeedPolicy.selectClaimCandidates` defensively excludes `finished` entries (staying pure — FR3); the feed cycle (serve / bare auto take), after `listReady`, declines each `finished` entry it sees (best-effort, failures logged and retried naturally on the next poll), then runs candidate selection over the rest. Explicit take checks the `finished` fact from `fetchTask` before claiming and refuses with the same decline call plus a non-success CLI outcome (FR4, FR5). *Rationale:* `FeedPolicy` is pure logic by design (no tracker access); side effects belong to the cycle that owns the tracker port. *Alternative rejected:* declining inside the adapter on `listReady` — a read operation acquiring write side effects breaks the port contract and NFR-P1's accounting.

**D5 — Restore status first, then comment; the transition winner comments.** Ordering: the instance performs the terminal-status restore, and only on success posts the explanation comment. *Rationale:* the status restore is the racing step — two instances declining concurrently resolve at the tracker (one transition succeeds meaningfully), so at most the winner comments in the common case (NFR-R1, NFR-R2); comment-first would double-comment on every crash-retry. *Trade-off accepted:* a crash between restore and comment leaves a silent restore — rare, recoverable by the operator reopening again, and the decline is still logged (NFR-O1).

## Risks / Trade-offs

- [Wire break: threads written by pre-split dev builds carry `report` markers no longer recognized — an old finish report would go invisible, so a reopened old task would be *worked*, not declined] → acceptable pre-production; reseed dev trackers and test fixtures; `GithubMarkerKind.fromWireValue` rejecting `"report"` makes stale fixtures fail loudly in tests rather than silently.
- [Boundary-list drift: PARK and FINISH must BOTH replace REPORT in `GithubClaimComment.isBoundary` and `GithubClaimLease.latestBoundaryIndex`, or session-ending anchoring silently weakens] → covered by the existing claim-lease boundary specs re-pointed at the new kinds; one shared boundary predicate is preferred over two copies.
- [Duplicate decline comments under a genuine concurrent race or crash-retry] → accepted per NFR-R1; state never corrupts, and the Ready-feed exit (D5) bounds it to the race window.
- [A human reopening a *closed* issue (state Gone) rather than relabeling Delivered] → covered by the same rule: any Ready-feed appearance with a finish report in history is declined (proposal Q2 resolved as "any path to Ready").
