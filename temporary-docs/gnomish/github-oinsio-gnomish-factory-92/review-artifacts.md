2. **WARNING — the recording stand-in of D1 has an undeclared existing counterpart** (`openspec/changes/kill-expensive-mutants/design.md:156`; `tasks.md:54-57`)
   Problem: D1 and task 2.1 introduce a `RecordingGit` helper (a script that answers nothing, appends argv and selected environment variables to a record file, exits 0), and the Sync-surfaces statement says "the change adds no parallel implementation". `GitProcessRunnerTransferSpec.recordingRunner()` (`adapters/git/src/test/groovy/com/github/oinsio/gnomish/adapter/git/GitProcessRunnerTransferSpec.groovy:205-219`) is already exactly that script — it answers the clone-key `rev-parse` and appends `argv=…`, `allow=[GIT_ALLOW_PROTOCOL]`, `count=[GIT_CONFIG_COUNT] key0=[…]`, the askpass pair and `global=[GIT_CONFIG_GLOBAL]` — and its "FR6, NFR-S2" feature (`:49-64`) already asserts the transfer environment reached the child, which is the assertion task 2.3 adds. `GitVersionCheckSpec.groovy:137` is a third argv-recording script.
   Impact: implemented as written, the module holds two recording stand-ins of one shape in one package with no marker at either end — the "undeclared pair" `manual-sync-pairs.md` names as an audit finding, and the rule's own trigger ("a change adding a second implementation … must either extract the shared abstraction or declare the pair") goes unanswered; `/audit-implementation` reports it. Task 2.3 also re-asserts what `GitProcessRunnerTransferSpec` already asserts, with no statement of why the existing feature is not the fast killer it is meant to become.
   Fix: in `design.md` D1, add: "`RecordingGit` is the one recording stand-in of the module: `GitProcessRunnerTransferSpec.recordingRunner()` builds its script through it (keeping its `argv=`, `allow=`, `count=`/`key0=`, `askpass=`/`ssh=`, `global=` record lines as the variables it asks `RecordingGit` to print), so the transfer-environment feature of task 2.3 is that spec's existing FR6 feature made first-killer, not a second one; `GitVersionCheckSpec`'s argv-only script stays its own (exemption: it answers `version` with a scripted version string, a decision stand-in, not a recorder)". Replace `design.md:156` "the change adds no parallel implementation" with "the recording stand-in of D1 extracts the shape `GitProcessRunnerTransferSpec.recordingRunner()` already spelled, so no second copy is added". Add a second row to the single-owner table: owner `RecordingGit` (`adapters/git/src/test`), consumers `GitProcessRunnerNetworkBranchSpec` and `GitProcessRunnerTransferSpec`, old way removed `recordingRunner()`'s inline script, enforcement: the `StallingGitOwnerSpec` scan extended with a second pattern (a script literal that appends `"$@"`/`$*` to a file) and the `GitVersionCheckSpec` exemption. Rewrite task 2.1 to "add `RecordingGit` and rewire `GitProcessRunnerTransferSpec.recordingRunner()` to it, assertions unchanged (NG3)", and task 2.3 to "move the transfer-environment kill to the existing FR6 feature of `GitProcessRunnerTransferSpec` (now built on `RecordingGit`), verifying its `numberOfTestsRun` ≤ 20 and `killingTest` = that feature; if the scoped PIT run shows the feature still recorded as slow, state the measured cause in the task report before adding a second feature".
   Fix risk: `GitProcessRunnerTransferSpec`'s assertions parse its own record lines, so `RecordingGit` must let a caller name the variables and the line format it prints (one more builder option than D1 lists); the exemption for `GitVersionCheckSpec` widens the scan's allowlist by one file.

3. **WARNING — the `StallingGit` builder surface cannot express two of its eight listed consumers** (`openspec/changes/kill-expensive-mutants/design.md:99-106, 126, 129`; `tasks.md:18-22`)
   Problem: The builder's answer option is `answer(String subcommand, String stdout, int exit)` — a literal answer keyed by subcommand alone. The D4 table says `TaskBranchLocatorSpec` and `StallingGitFixture` are "rewired" / "build through it", but their scripts need (a) an answer qualified by the second argument: `rev-parse --git-common-dir` → `.git`, any other `rev-parse` → exit 1 (`TaskBranchLocatorSpec.groovy:304-306`) or → the stalled tip (`StallingGitFixture.groovy:87-89`); (b) an answer read from a file *at run time*, which the spec rewrites after the script is written (`ls-remote) cat ${lsRemoteOut(dir)}; exit "$(cat ${lsRemoteExit(dir)})"`, `StallingGitFixture.groovy:90`; the trait's javadoc at `:12-18` says the files are rewritten to script what origin says after the kill); (c) side effects before the stall on the stalled subcommand — the attempts line, the push hook, the started marker (`StallingGitFixture.groovy:94-96`). `markOnStall` covers only (c)'s marker; `design.md:129` says "the hook stays a spec-side `answer` line", but an `answer` row for `push` would answer instead of stall.
   Impact: the sub-agent implementing task 1.4 cannot build those two scripts through the builder as specified; it either widens the API on its own (an undesigned surface the owner spec of task 1.5 then does not pin) or changes the fixtures' behaviour (an unqualified `rev-parse` answer, a frozen `ls-remote` answer), which breaks the specs implementing `StallingGitFixture` — the opposite of NG3.
   Fix: in `design.md` D4 and `tasks.md:18-22`, extend the builder with: `answer(List<String> argvPrefix, String stdout, int exit)` matched in declaration order, first match wins, with `answer(String subcommand, …)` as the one-element case; `answerWith(String subcommand, String shellFragment)` for an answer computed at run time (the `cat`/`exit "$(cat …)"` lines), used by `StallingGitFixture` for `ls-remote`; and `beforeStall(String shellLine)` appended in order before the `sleep` of every stalled subcommand, with `markOnStall(Path)` defined as `beforeStall("touch '<path>'")`. Update the two table rows: `TaskBranchLocatorSpec` → `answer(['rev-parse','--git-common-dir'], '.git', 0)`, `answer('rev-parse', '', 1)`, `answer('remote', …, 128)`; `StallingGitFixture` → `beforeStall` for the attempts line, the hook and the marker, `answerWith` for `ls-remote`. Add to task 1.2's `StallingGitSpec` one feature per new option. Replace "the hook stays a spec-side `answer` line" at `design.md:129` with "the hook is a `beforeStall` line".
   Fix risk: three more builder options to keep under the file-size cap and to cover in `StallingGitSpec`; `answerWith` accepts raw shell, so the javadoc must say it is for file-backed answers, not a second way to spell a stall (the owner spec's `sleep` scan still catches a stall written through it).
