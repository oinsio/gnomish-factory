# Gnomish Factory 0.1.0

The first release: the factory ships as a distribution archive. Install it with
Java 25 or newer and git 2.56.0 or newer on the machine:

1. Download `gnomish-0.1.0.tar.gz` (or `.zip`) and `SHA256SUMS` from this page.
2. Check the archive: `sha256sum -c --ignore-missing SHA256SUMS`; optionally
   `gh attestation verify gnomish-0.1.0.tar.gz --repo oinsio/gnomish-factory`.
3. Unpack it and put `gnomish-0.1.0/bin` on `PATH`.
4. `gnomish --version` prints `0.1.0`.

`bin/gnomish` checks for Java 25 or newer and passes every argument to the
factory unchanged; extra JVM options go in `GNOMISH_JAVA_OPTS`. The SBOM of the
factory jar is published beside the archives as `gnomish-0.1.0-cyclonedx.json`.

**git 2.56.0 or newer.** The factory checks `git --version` at startup and
refuses to run on an older git, with a line naming the floor and the version it
found. It turns off hooks defined in a clone's configuration with a switch that
git documents from 2.56 on, so an older git would ignore it. Many distributions
ship an older git. On macOS, or on Linux with Homebrew, install Homebrew's git
(`brew install git`) and put it first on `PATH`. On Ubuntu no package source
has 2.56 yet (the 26.04 archive ships 2.53, the `git-core` PPA 2.55), so build
git 2.56.0 from source. The repository's `scripts/install-git.sh` does that: it
installs the build tools with `apt-get`, downloads the kernel.org release,
checks it against a pinned SHA-256, builds and installs it under `/usr/local`
(or `--prefix DIR`), and checks the result against the floor. The git inside a
sandbox image is judged against its own floor, 2.51.0, until a later release
raises it.

## Upgrading from a build of the repository

If you ran the factory from a jar built out of the repository, everything it
kept now lives under the factory home (`~/.gnomish`, or `GNOMISH_HOME`), per
project. Nothing is migrated automatically. Before the first command of this
release, in this order:

1. **Finish or discard aborted tasks** with the build you have now: their
   worktrees live in the old folders that the next step deletes.
2. **Delete the old folders**: `rm -rf ~/.gnomish/logs ~/.gnomish/serve
   ~/.gnomish/worktrees`. At the next start, `git worktree prune` drops the
   clones' records of the deleted worktrees.
3. **Register every clone**: `gnomish project add <name> --dir=<path>`, once per
   clone. A command run in an unregistered directory stops and prints the line
   to paste.
4. **Move the secrets** out of environment variables into files: one file per
   secret, named exactly like the variable, mode `600`, in
   `~/.gnomish/projects/<name>/secrets/` (one project) or `~/.gnomish/secrets/`
   (every project). Environment variables are still read last.
5. **Move launcher options into the project file.** `--factory.*` options a
   wrapper script passed on every call belong in
   `~/.gnomish/projects/<name>/project.yaml`; `gnomish project show <name>` shows
   every setting with its origin. Delete the wrapper: `bin/gnomish` injects no
   options.
6. **Rename the default binding key.** `factory.bindings.default-binding`, the
   undocumented spelling that bound by accident, binds nothing any more; write
   `factory.bindings.default` (for example `factory.bindings.default: host`).
7. **Remove the hooks-path line from each clone, if you want your own hooks
   back.** Earlier builds wrote `core.hooksPath=<clone>/.git/gnomish-empty-hooks`
   into the clone's own `.git/config`, which kept your own git from running the
   clone's hooks. The factory no longer writes anything into the clone's
   configuration and removes nothing. Check with
   `git config --local --get core.hooksPath`; when the value ends in
   `/gnomish-empty-hooks`, run `git config --local --unset core.hooksPath`.

The operator guide's "Setting up a project" section describes the layout in
full.

## What's in 0.1.0

**Pipeline and quality control**
- Declarative pipelines in the target repository under `.gnomish/` (`config.yaml`,
  `pipeline.yaml`, `stages/<name>/stage.yaml`), fully validated before anything runs.
- A stage engine that drives one task from its recorded state to a terminal outcome, with
  four verify-check types: `builtin`, `command`, `external` and `judge` (LLM-as-judge with
  majority voting over an odd `votes` count).
- Quality failures re-run the stage with the findings as feedback until the attempt limit,
  then escalate with the full findings history; infrastructure failures retry the check and
  burn no attempt.
- `auto` and `manual` advancement: a manual checkpoint parks the task until a human approves it.
- External checks: GitHub Actions (verdict from workflow-run conclusions only) and a built-in
  `http` provider for other CI and quality services, behind an operator-owned egress allowlist.

**Commands**
- `gnomish run` — one ad-hoc task through the pipeline, no tracker. Headless: an escalation or
  a checkpoint exits 10 or 11 and is continued with `--resume --decision`.
- `gnomish take` — claim the head of the GitHub ready queue (issues labeled `gnomish:ready`),
  or act on given issues (`take 42 43`), and report back on the issue thread.
- `gnomish serve` — an autonomous daemon: N slots, a project-wide WIP limit, supervised
  background loops that are restarted rather than dying silently.
- `gnomish status` / `usage` — read-only task state and resource/cost usage from the task branch.
- `gnomish board` — the tracker as three columns (Ready, Working, AwaitingHuman), text or JSON.
- `gnomish dashboard` — one self-contained HTML page over the daemon snapshot, ledger and board.
- `gnomish project add|list|show` — register clones under the factory home (`~/.gnomish`).
- `gnomish doctor` — a read-only readiness checklist of the machine and a clone, each failure
  with its fix.

**Agents**
- Stages and judge votes run through the Claude Code CLI (`agent-cli` executor), with live
  progress, a decision-file protocol for questions to a human, and structured verdicts.

**State, resume and multi-instance safety**
- Stateless instances: the tracker holds coordination, the task's git branch holds the work and
  the state file; any instance resumes any task from its branch.
- Claim leases with heartbeats, a reaper for dead claims, takeover, and zombie fencing, so
  several instances can share one project.
- Every git process runs under the factory's own invocation policy (no clone hooks, no
  inherited configuration); requires git 2.56.0 or newer.
- Configurable task-branch bases with fail-closed escalation when the choice is ambiguous.

**Sandbox**
- By default, gnome processes run in an ephemeral container box (Docker); host execution is the opt-in
  legacy mode.
- Default-deny egress: the box sits on an internal-only network and reaches the outside only
  through the guard proxy and its allowlist.
- The published base image `ghcr.io/oinsio/gnomish-sandbox-base:0.1` (amd64, arm64) and the
  reference recipe in `share/sandbox-image/`.
- Label-based cleanup of the factory's Docker objects.

**Operator setup**
- One factory home per operator, one folder per registered project; layered configuration with
  one complete error report on a misplaced setting.
- Secrets read from files (mode `600`) or environment variables, never from yaml and never
  visible to the gnome; named vendor connection profiles.

**Extensibility**
- `gnomish-plugin-api`: trackers and external checks are discovered through `ServiceLoader`;
  the bundled GitHub adapter loads the same way a third-party plugin does.

**Not in this release:** Jira or any tracker other than GitHub; the `api` executor (direct
model calls) and agents other than Claude Code; pipeline routing by task type, stage
iteration, task hierarchies and epics; returning a claim before its lease expires.
