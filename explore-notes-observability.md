# Решения explore-сессии: daemon observability

> Временный файл — решения explore-сессии по пункту 5 роадмапа («Daemon
> observability»). Не для коммита. Записано 2026-08-01.

## Предложенные changes

1. `fix-reaper-idle-liveness` — предпосылка, найдена в этой сессии (Р8);
   уже создан, реализуется отдельно.
2. `add-serve-observability` — snapshot + ledger демона (Р2–Р7, Р9–Р14).
3. `add-board-command` — read-only доска трекера `gnomish board` (Р15);
   независим от п. 2, можно параллельно.
4. `add-dashboard-page` — self-contained HTML-«стена» поверх трёх
   поверхностей (Р16); после пп. 2–3 — зависит от форматов файлов и
   query-логики доски.

## Контекст

- Ограничения: ADR 0001 — нет web/actuator; NG3 add-factory-serve — никакого
  inbound HTTP; NFR-P2 — write-бюджет GitHub впритык (трекер как «дашборд
  демона» дорог по записям).
- Уже существующее сырьё: rolling-лог `~/.gnomish/logs/gnomish.log` с MDC;
  трекер-репорты per-task; `gnomish status` (read-only, JSON); per-task
  токены в status-report v1 (`totals.tokensByModel`); claim heartbeat.
- Предполагается реализованным: `fix-reaper-idle-liveness` — standing-режим
  heartbeat/reaper-треда в serve (см. Р8).

## Решения

### Р1. Три вопроса — три владельца, а не один «мониторинг»

- «Глубина очереди?» — вопрос к **трекеру** (read-only команда поверх
  существующих listReady / open-tasks listing; работает и без демона).
- «Жив ли, чем заняты слоты?» — вопрос к **инстансу** (snapshot-файл, Р4).
- «Что потрачено за ночь?» — вопрос к **истории** (append-only ledger;
  агрегация уже существующих per-task данных, не новый сбор).
- Алертинг — снаружи, поверх snapshot'а (Р7).

### Р2. Рамка «одиночка сейчас, флот потом»: файлы как контракт

- Минимальный вариант: демон пишет два локальных файла — snapshot
  (перезаписываемый, будущие gauges) и ledger (append-only JSONL, будущие
  события/counters). Расширение до флота — внешний коллектор, читающий эти
  файлы (node_exporter textfile / vector / OTel filelog / cron+scp); демон о
  флоте не узнаёт никогда. Push против pull не решаем — это деплойное
  решение коллектора; pull не нарушит NG3, т.к. inbound держит сайдкар.
- Плата за fleet-ready — только дисциплина формата: идентичность инстанса
  внутри данных (реюз instance id из lease-протокола + host + версия
  фабрики), `"version": 1`, конвенции status-report v1 (camelCase, ISO-8601
  UTC), атомарная запись snapshot'а (temp + rename), tail-дружественная
  ротация ledger'а.

### Р3. Чего сознательно не делаем

- Micrometer / OTel SDK внутри демона; система тегов; конфиг «куда слать»
  (у демона есть только «что», всё «куда» — в коллекторе).
- Агрегация по флоту в фабрике (общая плоскость флота — трекер).
- Heartbeat-issue в трекере (ест write-бюджет, операционный шум).
- Admin-socket / SIGUSR1-дамп (snapshot покрывает то же проще).
- Счётчики с момента старта в snapshot'е — территория ledger'а; итоги
  drain-прогона тоже только в ledger (никаких totals в stopped-записи).

### Р4. Состав snapshot'а

Snapshot отвечает ровно на «жив?» и «чем занят?», всё остальное — указатель
на канон (per-task — ветка задачи / `gnomish status <id>`, очередь — трекер,
история — ledger). Секции: `instance`, `lifecycle`, `feed`, `slots`,
`vitals`, `tracker`.

- `writtenAt` + `intervalSeconds` — файл самоописывает каденцию; staleness
  вычисляется без доступа к конфигу демона (`now - writtenAt > k×interval`).
- `lifecycle.state`: `running | draining | stopping | stopped`; при
  graceful-выходе пишется финальная `stopped`-запись с причиной; файл не
  удаляется (протухший mtime при `running` = умер, при `stopped` = штатно).
- `feed`: `state` (4 состояния автомата) + `since` + `lastPollAt` +
  `openFronts`/`wipLimit` (единственное «одолженное» у трекера число — feed
  и так держит его для своих решений; свежесть честно видна по lastPollAt).
- `tracker`: `lastSuccessAt`, `consecutiveFailures` — outage-тишина
  (NFR-R3) видна одним взглядом, не археологией логов.
- Не входят: глубина ready-очереди (в Full feed не опрашивает — поле врало
  бы), конфиг-дамп (кроме wipLimit), содержимое задач.

### Р5. Vitals — по тредам (сверено со спекой и кодом)

Тредовый инвентарь serve: feed loop (платформенный; в Full легитимно спит
без таймера), heartbeat+reaper (один виртуальный тред; reaper — duty его
тика, не тред), WorktreeJanitor (свой часовой таймер), слоты (виртуальный на
задачу), писатель snapshot'а (новый тред этого change — обязан быть
отдельным таймером: ни одна существующая петля не тикает гарантированно).

```json
"vitals": {
  "heartbeat": { "state": "idle | running | died",
                 "lastTickAt": "...", "heldClaims": 2 },
  "janitor":   { "lastRunAt": "..." }
}
```

- `heartbeat` — три состояния, не timestamp: `idle` — тревоги нет,
  `running` + `lastTickAt`, `died` — designed degradation D3 становится
  видимой полем, а не только строкой ERROR.
- Feed в vitals не входит: его здоровье полностью описывает секция `feed`,
  и читается только вместе с состоянием (свежесть lastPollAt обязательна в
  Filling/Idle, ничего не значит в Full). Reaper отдельной записи не имеет —
  его живость = живость heartbeat-треда.
- Писатель — сам себе vital: `writtenAt` и есть его пульс.

### Р6. Слоты — только занятые + capacity

```json
"slots": { "capacity": 3, "entries": [
  { "taskId": "42", "stage": "implement", "attempt": 2, "since": "..." } ] }
```

Слот = указатель (`taskId/stage/attempt/since`), не отчёт — детали через
`gnomish status <id>`. Загрузка = `entries.length / capacity`.

### Р7. Алертинг — снаружи, dead man's switch

- В коде демона алертинга нет. Operator guide описывает cron-скрипт поверх
  snapshot'а (путь стабилен между рестартами — каталог по instance-name,
  Р9): mtime свежий и инварианты держатся → исходящий ping
  (healthchecks-стиль); пропал ping — алерт. Исходящее направление не
  нарушает «no inbound HTTP».
- Правила для монитора (из полей snapshot'а):
  1. `writtenAt` протух при последнем `state: running` → демон умер (критично);
  2. `slots.entries` непусты ∧ `heartbeat.state ≠ running` (или lastTickAt
     протух) → claims протухают под живым демоном (критично);
  3. `feed.state: idleBlocked` с давним `since` → люди не разгребают
     эскалации (ожидаемый bottleneck, но о нём надо знать);
  4. `tracker.consecutiveFailures` растёт → outage;
  5. `heldClaims ≠ entries.length` дольше пары секунд → рассинхрон.

### Р8. Находка FR13 → решена отдельным change `fix-reaper-idle-liveness`

Найдено в этой сессии: reaper ехал только на claim-driven heartbeat-треде —
демон с нулём собственных claims не реапил вовсе (тупик после рестарта при
насыщенном W; зомби-задачи при пустой очереди — ломался сценарий FR12).
Принятое решение (вариант А + self-heal): standing-режим треда в serve
(пустой тик = ноль beats + reaper-duty; listOpen условный — бесплатно),
`ensureRunning()` из feed-цикла + существующее воскрешение на `register`,
явный stop в ServeShutdown, без анти-flap-backoff'а; fail-fast отложен до
packaging-change'а (супервизора пока нет). Реализовано в
`fix-reaper-idle-liveness` — observability строится поверх (в т.ч. `died`
в vitals).

### Р9. Расположение файлов: путь по instance-name, полный id — в данных

- Находка: `InstanceId` = `<name>-<суффикс>`, суффикс минтится заново на
  каждый процесс (D6 add-tracker-port). Путь по полному id ломал бы Р7:
  после рестарта snapshot переезжает, cron-монитор слепнет на старом файле;
  ledger фрагментируется, каталоги копятся.
- Решение: каталог `~/.gnomish/serve/<instance-name>/` (стабильная,
  конфигурируемая половина; D5 даёт нейтральный дефолт); полный id с
  суффиксом — внутри данных (Р2), рестарты различимы по содержимому.
- Два демона с одинаковым сконфигурированным именем на одном хосте —
  принятое ограничение (misconfiguration, документируем; без flock).

### Р10. Ledger: семантика — disposable history, не кэш

- Не перестраиваем (канон per-task — state-файл на ветке задачи, ветки
  смертны) и не канон (беречь не обязаны). Демон write-only: ни read-back,
  ни компакций, ни recovery при старте; ни одно решение демона от ledger'а
  не зависит; потеря файла операционно безвредна.
- Crash-consistency минимальна: flush построчно, без fsync; оборванная
  последняя строка допустима — читатель обязан переживать битую строку.

### Р11. Ledger: формат — типизированный JSONL, словарь из `TakeResult`

- Каждая строка: `"version": 1`, дискриминатор `type`, конвенции
  status-report v1, идентичность инстанса (полный id + host + версия).
- `taskOutcome` — на терминальный результат слота; `outcome` — имена
  sealed-вариантов: `delivered | awaitingHuman | aborted | revoked`
  (`parkReason` только при `awaitingHuman`). Все четыре несут ненулевой
  `finalState` → `totals` выводимы всегда, тем же путём, что
  `StatusReport.build()`. `EmptyQueue`/`Skipped` строк не порождают —
  правило: строку пишет только вариант с `finalState` (был engine-run —
  был расход). Поля: `taskId`, `outcome`, `parkReason?`, `stage` (nullable,
  null при pipelineEnd), `attemptsUsed`, `startedAt`/`finishedAt`,
  `wallTimeSeconds?`, `tokensByModel`.
- Точка врезки — `TakeSlotRunner`, рядом с `drainReport.record()` (javadoc
  `DrainReport` сам предсказывает «machine-findable structured summary» как
  отложенную задачу — ledger и есть она). Слот сегодня не знает свой
  `startedAt` (`SlotLedger` хранит голый `Set<TaskRef>`) — доработка общая
  со snapshot'ом (Р6 `slots.entries[].since`).
- `runSummary` — только у drain-прогона (естественная граница): счётчики по
  исходам + суммарные `tokensByModel` + длительность; осознанный
  convenience-дубль taskOutcome-строк. Standing-режим `runSummary` не пишет
  ни при каком stop — «итоги за аптайм» суть счётчики-с-момента-старта,
  отвергнутые Р3; читатель агрегирует строки сам.
- `lifecycle` — строки `started`/`stopped` (с причиной) включаем: snapshot
  держит только последнее состояние, а тихий crash-loop на пустой очереди
  без них в ledger'е невидим вовсе (восстановление рестартов по смене
  суффикса в taskOutcome работает, только если между рестартами завершались
  задачи). Без totals в `stopped` (Р3).

### Р12. Ledger: ротация — дневные файлы, UTC

- `ledger-YYYY-MM-DD.jsonl`, граница суток по UTC (конвенция Р2). Живой
  файл никогда не переименовывается — ротация = демон начинает писать в
  файл с новым именем; «за ночь» = 1–2 файла по имени.
- Retention: sweep «удалить старше N дней» — duty писателя snapshot'а (тред
  уже тикает; observability-писатель владеет observability-файлами; janitor
  не трогаем — он worktree-специфичен). Один конфиг-параметр, 0 = хранить
  вечно.

### Р13. Ledger: конкурентность — один appender, synchronized построчно

- Слоты финишируют конкурентно → один разделяемый appender-объект,
  `synchronized` append+flush на строку. Межпроцессной защиты не нужно:
  один демон на каталог — следствие Р9.

### Р14. Триггер snapshot'а: таймер + немедленно на переходах

- Таймерный beat (каденция самоописана `writtenAt` + `intervalSeconds`,
  Р4) плюс немедленная запись на переходах — именно она делает финальную
  `stopped`-запись и `died` в vitals своевременными; таймер один такой
  гарантии не даёт. Staleness-математика Р4 не ломается: interval — это
  максимальный зазор, немедленные записи его лишь уплотняют.
- Писатель остаётся однопоточным: переход взводит dirty-флаг / будит
  писателя, а не пишет сам (две точки триггера — одна точка записи);
  атомарность temp + rename из Р2 сохраняется.

### Р15. Команда очереди: `gnomish board` — доска трекера, отдельный change

- Находка: слот голого `status` занят — `gnomish status --dir` без task id
  уже листает task-ветки клона (add-git-workflow, FR13); `--dir` обязателен.
  `status` целиком принадлежит владельцу «канон per-task» из Р1. Расширять
  его трекером — флаг молча менял бы источник данных; отвергнуто, как и
  неймспейсы (`tracker status`) в плоском CLI.
- Имя: `gnomish board` («queue» недопродаёт, «status» занят). Трекер для
  оператора — буквально доска; три ведра = её колонки:
  - **Ready** — `listReady`: порядок очереди, `returned`; обязательная
    backoff-аннотация реюзом core-фильтра поверх `abortFacts` («в очереди
    7, демону доступно 5, две в backoff до T») — иначе «почему демон не
    берёт 42?» без ответа;
  - **Working** — `listOpen`: `Working(holder)` + `claimVersion` — готовый
    вид на весь флот (Р2: общая плоскость флота — трекер);
  - **AwaitingHuman** — `listOpen`: `ParkReason` = расшифровка `idleBlocked`
    из правила 3 Р7 (`escalation` / `infra` / `checkpoint`).
- Титулы: `TaskRef` — голый id; добавить `title` в `ReadyTask`/`OpenTask` —
  адаптеры титул в list-вызовах уже держат и роняют при маппинге (без N+1
  fetchTask); цена — порт-типы, оба адаптера, контрактные спеки. Проверить
  при проектировании, что Jira-поиск тоже отдаёт summary.
- Вывод: текст + `--json` (как `status`); JSON даёт cron-монитору
  tracker-side правила («очередь растёт», «эскалации висят») без демона —
  дополнение к snapshot-правилам Р7 от второго владельца.
- Скоуп: отдельный маленький change (`add-board-command`), не секция
  `add-serve-observability` — порт-изменение тянет адаптеры и спеки;
  observability-change остаётся чистым «демон пишет два файла». Работает
  без демона. Границы: board — команда трекер-владельца, snapshot демона в
  неё не подмешивать; «всё сразу» — будущая композиция поверх трёх
  поверхностей, не размывание одной.

### Р16. HTML-дашборд: `gnomish dashboard`, self-contained + `--watch`

- Тезис: HTML-страница ≠ HTTP-сервер — NG3/ADR 0001 не нарушаются. Демон
  не тронут вообще: рендерер — ещё один читатель файлового контракта Р2,
  презентация вне демона ровно по Р3. Это и есть «композиция поверх трёх
  поверхностей» из Р15: snapshot (жив? чем занят?) + ledger (история) +
  доска трекера; секции деградируют независимо (нет snapshot'а — «демон не
  запускался», нет сети — доска «unavailable»).
- Форма: file:// не умеет fetch (CORS) → self-contained страница с
  запечёнными данными (данные/JS/CSS инлайном, ноль внешних запросов).
  One-shot по умолчанию (приложить к тикету); `--watch` — перегенерация
  каждые ~10 с + `<meta http-equiv="refresh">`: живая «стена» без единого
  сервера (file:// сам себя перечитывает, блокируется только fetch).
- Два слоя протухания, оба видимы (wall-режим иначе молча врёт):
  1. демон умер → snapshot протух — вычисляется из `writtenAt` +
     `intervalSeconds` (Р4), секция краснеет по правилам Р7;
  2. `--watch`-рендерер умер → страница перестала перегенерироваться —
     запечённый `generatedAt` + инлайн-JS против часов браузера
     (`now - generatedAt > k×refresh` → баннер на всю страницу);
     meta-refresh этого не заменяет.
- Три каденции: snapshot + ledger — каждый цикл (локальные файлы,
  бесплатно); доска трекера — ~60 с с кэшем между циклами (вечная вкладка
  не жжёт rate limit; секция несёт свой «обновлено в T» à la lastPollAt).
- История v1: агрегат ledger'а за последние N дней (исходы по дням, токены
  по моделям) — таблица + CSS-бары; никаких чартовых библиотек/CDN/шрифтов
  (self-contained). Захотелось настоящих графиков → сигнал уходить в
  textfile-экспорт + Grafana по Р2, а не растить страницу.
- Мелкое: дефолт вывода — `dashboard.html` в каталоге инстанса (Р9),
  `--out` для переопределения; дизайн-цель «один экран» (meta-refresh
  сбрасывает скролл), per-task детали — указателями на канон в духе Р4;
  никакого Thymeleaf — строковый шаблон, брат `StatusTextRenderer`;
  флота на странице нет (агрегация флота — внешний коллектор, Р2–Р3).
- Скоуп: третий change (`add-dashboard-page`), после первых двух — зависит
  от форматов файлов и от query-логики доски из `add-board-command` (реюз
  composition + backoff-аннотации кодом, не шелл-аут).

## Открытые вопросы (следующие шаги сессии)

- Не осталось — все пункты сессии закрыты (Р1–Р16). Следующий шаг —
  proposal'ы: `add-serve-observability` (snapshot + ledger, Р2–Р7, Р9–Р14),
  `add-board-command` (Р15), затем `add-dashboard-page` (Р16).
